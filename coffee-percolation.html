Water through coffee grounds — the same model on two backends

Four states, one lattice, one initial condition, run twice. Left uses backend="block"; right uses backend="neighborhood". Watch the bottom row of each table.

A radius-1 synchronous cellular automaton cannot conserve mass, at any number of states. Two water cells sitting diagonally above one empty cell each independently see “empty below me” and vacate; the empty cell sees water above and fills. Two in, one out. Preventing that needs the losing cell to know it lost — to see its competitor, two cells away — and radius 2 on a hex grid is 18 neighbours, so an anisotropic rule table would be k¹⁹. It is not a bug in the rule below; it is a property of the neighbourhood.

Block partitioning fixes it by construction. The rule rewrites a whole 3-cell triangle at once, so arbitration happens inside the block and a rule that permutes multisets is exactly conservative with no bookkeeping. This is the lattice-gas approach — FHP is the hexagonal precedent — and it is the entire reason @hexlife/embed/ca ships two backends instead of one general loop.

The failure mode is worth naming, because it does not look like one. The right-hand grid stays perfectly plausible throughout — water beads, soaks in, spreads down. Only the number moves. It moves in both directions, too, for want of the same arbitration: two sources feeding one destination lose mass, one source feeding three destinations duplicates it. This seed loses ~4% on the first tick and then runs away upward, finishing with roughly 4.5× the water it started with — an espresso puck that brews more coffee than you poured.

The left-hand world eventually stops: water pools, the reachable grounds are wet, and nothing can change again. The engine notices that a settled world is a fixed point it can never leave and stops scheduling frames entirely — “settled” under the grid is the element reporting it, not a stall.

block — 3-cell triangle, k³ table

Transport and wetting are both rewrites of a whole triangle, so no two cells can ever claim the same destination. Total water is held to the count, forever — then it comes to rest.

neighborhood — radius 1, k⁷ table

The most natural radius-1 expression of the same model: water vacates when there is somewhere below to go, open space fills from above, ground wets on contact. Nothing arbitrates.

Why 66 rows and not 64

Block mode partitions the grid into up-triangles in three phases, cycling φ = tick mod 3. The partition is seamless only if the sublattice residue survives the row wrap, which needs rows ≡ 0 (mod 3). The embed's usual default of 64 does not qualify, and <hexlife-ca> shows an error box rather than rounding it — the grid you asked for should not silently become a different grid. 63 and 66 both work; 66 keeps the two grids here identical, since the neighborhood backend has no such constraint.

What the block rule actually is

Two steps, applied to the block's three cells in vertex order — top, middle, bottom. 

// 1. Wetting. One water meets one dry ground: the water is absorbed, the ground turns wet.
//    NOT a permutation of the multiset — {water, dry} → {air, wet} is a reaction, and
//    `isConservative` says so. What it does preserve is water TOTAL: free + bound.
// 2. Gravity. Ground is immobile; among the slots holding air or water, water sinks.
//    A permutation of the mobile slots, so exactly conservative on its own.

Note what the library reports about it: not conservative (step 1 is a reaction) and not isotropic (step 2 singles out “down”). Both are correct and both are deliberate. isConservative and isIsotropic are reported, never enforced — reactions, sources and sinks are legitimate models, and breaking isotropy is precisely how you get gravity on a lattice that is otherwise perfectly symmetric. The invariant this model actually claims is the narrower one on the bottom row of each table, and the page checks it over all 64 block entries at load before running a single tick.

Why this lattice

A hex grid has one neighbour class — six neighbours, all equidistant. A square grid has two, and the resulting anisotropy is not cosmetic: six-fold symmetry is sufficient for a lattice gas to recover isotropic hydrodynamics in the continuum limit and four-fold is not, which is why square-lattice automata grow diamond-shaped fronts where physics wants circles. Hex cell centres also form a triangular lattice, where site percolation has p_c = 1/2 exactly — on the square lattice it is ≈0.5927, known only numerically. The grounds below are packed at 0.45, so the pore space is at 0.55, comfortably above threshold: the water gets through, and it does so for a reason with a closed form.

The grid is a torus in both axes and this model has no floor, so water that reaches the bottom re-enters at the top and keeps circulating. That is deliberate — it keeps transport visible indefinitely, and it leaves the census claim completely clean.

Running this page

It resolves @hexlife/embed from jsDelivr through the import map in the page source, so it needs a network but no build. To point it at a local npm run build:embed instead, swap that one block for the commented-out map beside it — nothing else in the page changes, which is the reason it is written with bare specifiers rather than URLs.

Serve it with any plain static file server. Not npm run dev: Vite resolves bare specifiers in inline module scripts itself, at transform time, so it fails on @hexlife/embed/ca before the browser ever sees the import map.
